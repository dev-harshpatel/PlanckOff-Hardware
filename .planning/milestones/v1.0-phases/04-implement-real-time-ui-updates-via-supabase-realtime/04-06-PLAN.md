<objective>
Wire Realtime in-memory patching for the remaining 3 tables: `project_pricing_items`, `project_pricing_proposal`, and `projects`. This is the second of two callback-implementation plans. After this plan + 04-05 land, all five tables are fully wired.

The wiring follows the threading map from RESEARCH.md "Callback Wiring Map":

```
useProjectRealtime.ts
  ├── project_pricing_items     → callback defined in PricingReportConfig.tsx (setPrices)
  ├── project_pricing_proposal  → callback defined in usePricingProposal.ts (setProfitPct etc.)
  └── projects                  → callback defined in ProjectContext.tsx (setProjects via inline transform)
```

Because the callbacks live in deeper files but `useProjectRealtime` is invoked inside `useProjectData`, we thread the callbacks UP via props: `usePricingProposal` returns its callback → `PricingReportConfig` aggregates it with its own → `PricingReportConfig` passes both up via a prop on whatever component owns `useProjectData`. That ownership boundary is `ProjectViewClient.tsx` (or equivalent — the executor must locate it). To minimise prop-drilling, this plan instead exposes a setter-style API: `useProjectData` accepts a `realtimeCallbacks` prop and `PricingReportConfig` reaches the same `useProjectData` instance via React Context — i.e. the callbacks go DOWN via context.

To keep the change self-contained, this plan uses a lightweight pattern: `useProjectData` exposes two ref setters (`setPricingItemsCallback`, `setPricingProposalCallback`) that downstream consumers call from a `useEffect`. The refs are wired directly into `useProjectRealtime`'s callback options. This avoids re-mounting/re-subscribing whenever pricing components mount or unmount, and keeps `useProjectData`'s API additive (no breaking change to its existing call sites).

The `projects` table is simpler: its callback lives in `ProjectContext.tsx` itself, since `ProjectContext` already holds the projects list state. We add a separate channel inside `ProjectContext` for ONLY the `projects` table — scoped per-project requires knowing which project we're viewing, which `ProjectContext` does not know directly. RESEARCH.md "Open Question 2" recommends scoping to current project only via `useProjectRealtime`. To honour D-07 (single hook) AND keep `ProjectContext` decoupled from `useProjectData`, this plan uses the same ref-setter pattern: `ProjectContext` exposes `updateProjectFromRealtime(payload)`; `useProjectData` calls a setter to register that function as the `onProjectChange` callback for its scoped Realtime channel. This way the single `useProjectRealtime` hook still owns the subscription, and `ProjectContext.setProjects` is invoked via the registered callback.
