## Phase 1: Beautify Exports & Fix Ordering

**Goal:** Every PDF and Excel export in the application shares an identical visual template and reflects the exact row order the user sees in the UI — no reordering, no visual inconsistency.

**Requirements:** PDF-01, PDF-02, PDF-03, PDF-04, PDF-05, PDF-06, PDF-07, XLS-01, XLS-02, XLS-03, ORD-01, ORD-02, ORD-03, ORD-04, VER-01

**UI hint**: yes

**Success Criteria:**
1. A side-by-side comparison of Door Schedule, Hardware Sets, and Pricing PDFs shows identical header, footer, fonts, colors, and table styling
2. Every exported PDF has a company logo, project name, and export date in the header, and page numbers in the footer
3. Page 2+ of any multi-page PDF repeats column headers at the top — no row is split mid-record
4. Every exported Excel file has bold colored header row, non-truncating column widths, and a frozen top row
5. The row sequence in exported Door Schedule PDF matches the row sequence visible in the UI at export time (tested with custom sort applied)
6. Same ordering guarantee verified for Hardware Sets and Pricing exports

## Phase 2: Implement Error Message Registry

**Goal:** Every user-facing error in the application comes from a single typed registry — no inline strings, no raw JS errors shown to users, no inconsistent copy.

**Requirements:** ERR-01, ERR-02, ERR-03, ERR-04, ERR-05, ERR-06, ERR-07

**UI hint**: yes

**Success Criteria:**
1. A `constants/errors/` directory exists with domain files (`auth.ts`, `doors.ts`, `hardware.ts`, `pdf.ts`, `general.ts`) each exporting typed error objects
2. A reusable `<ErrorDisplay>` component renders any registry error consistently with the app's Tailwind/shadcn theme
3. Grep for hardcoded inline error strings in components, hooks, and services returns zero matches (outside the registry)
4. Auth failures, API errors, validation failures, file upload failures, and AI extraction failures all map to named registry entries
5. No raw `error.message`, stack trace, or API response body is ever shown to the user — all fall back to a generic registry entry
6. The toast system, inline form errors, and modal error states all use the same `<ErrorDisplay>` component or a consistent pattern from the registry

## Phase 4: Implement Real-Time UI Updates via Supabase Realtime

**Goal:** Every table that drives UI state (doors, hardware sets, projects, pricing) has a Supabase Realtime `postgres_changes` subscription wired into the relevant React context or hook, so any insert, update, or delete is reflected in the UI instantly without a page reload or manual re-fetch. Optimistic updates for user-triggered writes and proper cleanup on unmount are included.

**Requirements:** RT-01, RT-02, RT-03, RT-04, RT-05, RT-06, RT-07, RT-08

**UI hint**: yes

**Success Criteria:**
1. Any update made by the user is reflected in the UI instantly without a page reload or manual re-fetch
2. In a multi-tab scenario, a change made in Tab A is automatically reflected in Tab B within 1–2 seconds
3. Optimistic updates roll back cleanly if the server write fails, with an appropriate error message shown
4. No stale subscriptions or memory leaks on navigation between pages
5. Works correctly alongside any caching layer — cached data does not override a fresh Realtime update
6. Subscription reconnection on network drop is handled gracefully (no manual reload needed)
